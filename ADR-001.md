# ADR-001: Pipeline Asíncrono de Inteligencia Deportiva y Telemetría Multi-LLM

## Estado
Aceptado e Implementado (Producción) — Agosto 2026

## Contexto y Desafío Operativo
El entrenamiento de resistencia de alto rendimiento exige comparar continuamente la planificación técnica (prescripción de ritmos por bloques) contra la ejecución real en campo (laps manuales en reloj GPS).

* **Problema:** Los dashboards tradicionales (Garmin Connect, Strava) ofrecen métricas estáticas pero carecen de una capa de síntesis cualitativa que integre contexto fisiológico (CTL/ATL/TSB), biométrico (HRV/RHR), condiciones climáticas exactas y el plan prescripto por el entrenador.
* **Restricción Operativa:** El sistema debe operar con costo de infraestructura $0/mes, de forma desatendida (serverless) y con tolerancia a fallos de cuota o indisponibilidad de proveedores de IA.

---

## Decisiones Técnicas Clave

### 1. Ingesta y Capa de Datos (Intervals.icu REST API + Open-Meteo)
* **Decisión:** Utilizar Intervals.icu como single source of truth para telemetría deportiva y Open-Meteo Archive API para condiciones meteorológicas.
* **Alternativas evaluadas:** Garmin Health API / Strava Webhooks (requieren aprobación empresarial o presentan rate limits severos).
* **Justificación:** Intervals.icu consolida laps de Garmin, modelado de fatiga Banister (CTL/ATL/TSB) y eventos planificados vía un único endpoint REST autenticado por API Key estática. Open-Meteo permite resolver temperatura/humedad histórica por coordenadas a costo $0 y sin autenticación.

### 2. Orquestación Serverless (GitHub Actions CI/CD)
* **Decisión:** Automatizar la ejecución diaria vía GitHub Actions mediante cron (02:00 UTC / 23:00 ART) y soporte para `workflow_dispatch`.
* **Alternativas evaluadas:** AWS Lambda + EventBridge, VM Always-Free en Oracle Cloud, n8n auto-hospedado (descartado por sobrecarga de mantenimiento de infraestructura).
* **Justificación:** Mantenimiento cero de servidores, control de versiones nativo junto al código, gestión segura de secretos y disponibilidad de runners Ubuntu gratuitos con soporte de Docker.

### 3. Capa de Inferencia (Multi-LLM Fallback Pattern)
* **Decisión:** Arquitectura de inferencia redundante: Nodo Principal con **Gemini 3.6 Flash** y Failover automático con **Groq Cloud (Llama 3.3 70B Versatile)**.
* **Alternativas evaluadas:** Dependencia única de OpenAI GPT-4o o Anthropic Claude (costos variables por consumo / sin Free Tier serverless permanente).
* **Justificación:** Si Google actualiza endpoints o satura cuotas de uso, Groq resuelve la inferencia en <1 segundo manteniendo el costo mensual en $0 absoluto y garantizando un SLA del 100% en el despacho diario.

### 4. Modelo de Dominio Adaptativo (Lapeado Manual y Detección de Modo)
* **Decisión:** Normalizar diferencias de ritmos en min/km, parsear laps manuales y bifurcar el tono analítico según la tipología de sesión (Competición vs. Entrenamiento).
* **Justificación:** Refleja la práctica real del atleta en pista/calle, permitiendo evaluar la estrategia táctica (negative splits) en carreras y el apego a zonas cardíacas en entrenamientos de calidad.

## Consecuencias y Trade-offs

* **Ventajas:** Latencia total de pipeline <30 segundos, costo operativo $0.00, resiliencia ante caídas de proveedores de IA y retroalimentación personalizada diaria por correo.
* **Limitaciones mitigadas:** La sincronización de TrainingPeaks vía cookies de sesión (`Production_tpAuth`) se encapsula en Docker con directiva `continue-on-error: true`, evitando que fallos de autenticación de terceros interrumpan el análisis principal de Garmin.
